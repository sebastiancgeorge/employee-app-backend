What is Pydantic?

Pydantic is Python's most popular data validation library. You define a class, declare the fields and their types, and Pydantic handles the rest.

Three things it gives you (for free)

FeatureWhat it does
ValidationRejects bad data before your code ever runs
SerializationConverts Python objects → JSON-safe dicts
DocumentationFastAPI reads your schema to generate Swagger docs

Key idea: Define the shape of data once as a class, and Pydantic validates incoming data, serializes outgoing data, and documents your API — all from that one definition.

pydantic-settings — Config from Environment

BaseSettings works like BaseModel, but reads values from environment variables and .env files instead of JSON bodies.

Without pydantic-settings
import os

db_url = os.getenv("DATABASE_URL")
# could be None — no error
# until you actually use it!

debug = os.getenv("DEBUG")
# returns "true" (a string)
# not True (a bool)
With pydantic-settings
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    database_url: str              # required
    app_env: str = "development"  # optional
    debug: bool = False          # auto-coerces

    model_config = SettingsConfigDict(
        env_file=".env",
    )

settings = Settings()

Why this matters

FeatureWhat it does
Fail-fast validationMissing DATABASE_URL? App crashes at startup with a clear error — not later at the first DB query
Type coercion"true" → True, "5433" → 5433 — automatic
.env file supportNo separate python-dotenv needed — built in
Single source of truthAll config in one class — easy to find, easy to document

In this project: See config.py — it loads DATABASE_URL, APP_ENV, and DEBUG from .env in development, and from real environment variables in staging/production.

01

Request & Response Schemas

Replacing raw dicts with typed, validated models

The Problem: Raw dict Bodies

Our employees router accepted input as a raw dict:

@router.post("", status_code=status.HTTP_201_CREATED)
def create_employee(body: dict = Body(...), db: Session = Depends(get_db)):
    return employee_service.create(db, body.get("name"), body.get("email")).to_api_dict()

What could go wrong?

  • Client sends {"nme": "Alice"} (typo) — no error, name is silently None
  • Client sends {"name": 123, "email": true} — accepted, crashes later
  • Client sends {"name": "Alice", "email": "a@b.com", "hack": true} — extra key silently ignored
  • Swagger docs cannot show what fields are expected

The Fix: BaseModel

Define a Pydantic schema for the request body:

from pydantic import BaseModel, ConfigDict, EmailStr, Field

class EmployeeCreate(BaseModel):
    model_config = ConfigDict(str_strip_whitespace=True, extra="forbid")
    name:  str       = Field(min_length=1)
    email: EmailStr
    age:   int | None = None

What we get

  • name must be a non-empty string — Field(min_length=1)
  • email must be a valid email — EmailStr
  • age is optional — defaults to None
  • Whitespace stripped before validation — str_strip_whitespace
  • Extra keys rejected — extra="forbid"

In the router

@router.post("", ...)
def create_employee(
    body: EmployeeCreate,
    db: Session = Depends(get_db),
):
    return employee_service.create(db, body)

FastAPI validates the body before your function runs.

Field() Constraints

Pydantic's Field() lets you add validation rules directly on the field definition:

from pydantic import BaseModel, Field

class EmployeeCreate(BaseModel):
    name:  str       = Field(min_length=1)  # must not be empty
    email: EmailStr                        # validated email format
    age:   int | None = None               # optional field
ConstraintApplies toMeaning
min_lengthstrMinimum string length
max_lengthstrMaximum string length
geint / floatGreater than or equal to (≥)
leint / floatLess than or equal to (≤)
gtint / floatStrictly greater than (>)
patternstrMust match a regex pattern
defaultanyDefault value if not provided

model_config — Class-Wide Settings

Configure behavior for the entire schema using ConfigDict:

from pydantic import BaseModel, ConfigDict

class EmployeeCreate(BaseModel):
    model_config = ConfigDict(
        str_strip_whitespace=True,   # "  Alice  " → "Alice"
        extra="forbid",              # reject unknown keys
    )
    name: str = Field(min_length=1)
SettingEffect
str_strip_whitespace=TrueAuto-strips leading/trailing spaces from all str fields
extra="forbid"Raises error if client sends unknown keys
extra="ignore"Silently drops unknown keys (default)
from_attributes=TrueRead data from object attributes (ORM models) instead of dicts

Tip: Use extra="forbid" on request schemas to catch typos early. Use from_attributes=True on response schemas to serialize ORM objects.

response_model — Controlling the Output

Tell FastAPI what shape the response should have:

Before (raw dict)
@router.get("/{employee_id}")
def get_employee(
    employee_id: int, ...
):
    return employee_service \
        .get_by_id(db, employee_id) \
        .to_api_dict()

# Returns everything including
# deleted_at, internal fields...
After (response_model)
@router.get(
    "/{employee_id}",
    response_model=EmployeeResponse,
)
def get_employee(
    employee_id: int, ...
):
    return employee_service \
        .get_by_id(db, employee_id)

# Pydantic serializes & filters!

What response_model does

  • Serializes the return value through the Pydantic schema
  • Only fields declared in the schema appear in the JSON
  • Generates accurate Swagger response documentation
  • Acts as a security allowlist — internal fields never leak

What Happens When Validation Fails?

FastAPI returns a 422 Unprocessable Entity with details about every error:

Bad request
POST /employees
{
  "name": "",
  "email": "not-an-email",
  "age": -5,
  "secret": "hack"
}
422 response
{
  "detail": [
    {"loc": ["body","name"],
     "msg": "String should have at
            least 1 character"},
    {"loc": ["body","email"],
     "msg": "value is not a valid
            email address"},
    {"loc": ["body","age"],
     "msg": "Input should be >= 0"},
    {"loc": ["body","secret"],
     "msg": "Extra inputs are not
            permitted"}
  ]
}

Notice: ALL errors are reported at once, not just the first one. This makes it easy for the client to fix everything in one go.

Custom Validators & Nested Schemas

Going beyond built-in constraints

@field_validator — Single-Field Rules

When Field() constraints are not enough, write a custom validator:

from pydantic import BaseModel, Field, field_validator

class AddressCreate(BaseModel):
    line1:       str = Field(min_length=1, max_length=255)
    city:        str = Field(min_length=1, max_length=120)
    postal_code: str = Field(min_length=1, max_length=32)
    country:     str = Field(min_length=1, max_length=120)

    @field_validator("postal_code")
    @classmethod
    def validate_postal_code(cls, v: str) -> str:
        if not v.isdigit():
            raise ValueError("Postal code must contain only digits (0-9)")
        return v

Rules for @field_validator

  • Decorate with @field_validator("field_name") and @classmethod
  • Receives the field value (already type-checked) as v
  • Raise ValueError to reject — Pydantic converts it to a 422 error
  • Return the (possibly transformed) value

Alternatives to @field_validator

  • Field(pattern=...) — digits only like isdigit(): postal_code: str = Field(min_length=1, pattern=r"^\d+$")
  • Database CHECK constraint so invalid values cannot be stored even if the API is bypassed

EmailStr — Built-In Email Validation

Pydantic ships with an email type (requires pydantic[email]):

Before
class EmployeeCreate(BaseModel):
    name:  str = Field(min_length=1)
    email: str = Field(min_length=1)
    # accepts "not-an-email" !
After
from pydantic import EmailStr

class EmployeeCreate(BaseModel):
    name:  str      = Field(min_length=1)
    email: EmailStr
    # rejects anything without @

Install: pip install pydantic[email] (or add "pydantic[email]>=2.0.0" to pyproject.toml).

What it checks: Format follows RFC 5322. It does NOT verify the mailbox exists.

@model_validator — Cross-Field Rules

Sometimes one field's rule depends on another — here postal_code length depends on country (after each field is validated on its own):

from pydantic import BaseModel, ConfigDict, Field, field_validator, model_validator

class AddressCreate(BaseModel):
    model_config = ConfigDict(str_strip_whitespace=True, extra="forbid")

    line1:       str = Field(min_length=1)
    city:        str = Field(min_length=1)
    postal_code: str = Field(min_length=1)
    country:     str = Field(min_length=1)

    @field_validator("postal_code")
    @classmethod
    def validate_postal_code(cls, v: str) -> str:
        if not v.isdigit():
            raise ValueError("Postal code must contain only digits (0-9)")
        return v

    @model_validator(mode="after")
    def postal_code_length_for_country(self):
        country = self.country.strip().upper()
        n = len(self.postal_code)
        if country in ("US", "USA") and n != 5:
            raise ValueError("US ZIP codes must be exactly 5 digits")
        elif country == "IN" and n != 6:
            raise ValueError("Indian PIN codes must be exactly 6 digits")
        return self

Other countries: only the digit rule applies (any length ≥ 1). See employees/schemas.py — AddressCreate.

@field_validator vs @model_validator

@field_validator@model_validator
ScopeOne field at a timeEntire model (all fields)
AccessReceives field value vReceives self (all fields)
Use caseFormat checks, rangesCross-field dependencies
DecoratorNeeds @classmethodNo @classmethod for mode="after"

Nested Schemas

Real APIs return nested objects. Pydantic schemas can contain other schemas:

class DepartmentMinimalResponse(BaseModel):
    model_config = ConfigDict(from_attributes=True)
    id:   int
    name: str

class AddressResponse(BaseModel):
    model_config = ConfigDict(from_attributes=True)
    id:          int
    line1:       str
    city:        str
    postal_code: str
    country:     str

class EmployeeResponse(BaseModel):
    model_config = ConfigDict(from_attributes=True)
    id:    int
    name:  str
    email: EmailStr
    age:   int | None
    departments:      list[DepartmentMinimalResponse] | None
    addresses: list[AddressResponse] | None

Key point: Each nested object is validated by its own schema. If a department is missing name, you get a clear error — even inside a nested list.

from_attributes = True

How Pydantic reads data from SQLAlchemy ORM objects (instead of dicts):

Without from_attributes
# Pydantic expects a dict:
EmployeeResponse(**{
    "id": 1,
    "name": "Alice Smith",
    "email": "alice@example.com",
    ...
})

# So you need .to_api_dict()
# on every ORM object!
With from_attributes
class EmployeeResponse(BaseModel):
    model_config = ConfigDict(
        from_attributes=True
    )

# Now Pydantic reads .id, .name, .email
# directly from the ORM object:
emp = db.query(Employee).first()
EmployeeResponse.model_validate(emp)
# FastAPI does this automatically
# when you set response_model

Bottom line: With from_attributes=True and response_model, you return the ORM object directly from your service — no manual .to_api_dict() needed.

Response Filtering & Security

Controlling what the client sees

The Problem: Leaking Internal Data

When you return raw dicts or ORM objects without a response schema, everything goes to the client:

// What the client sees when there is no response schema:
{
  "id": 1,
  "name": "Alice Smith",
  "email": "alice@example.com",
  "age": 28,
  "deleted_at": null,           // internal soft-delete flag
  "password_hash": "$2b$12...", // if we add auth later!
  "internal_notes": "..."      // any future internal field
}

Why this is dangerous

  • New columns added to the database are automatically exposed to every client
  • Soft-delete flags, password hashes, audit trails — all visible
  • You have to remember to exclude fields manually every time
  • One forgotten field = a security vulnerability

Response Schemas = Allowlist

A response schema declares exactly which fields the client should see. Anything not listed is automatically excluded.

ORM model (all fields)
class Employee(Entity):
    name:       str
    email:      str
    age:        int | None
    # inherited from Entity:
    id:         int
    created_at: datetime
    updated_at: datetime
    deleted_at: datetime | None
Response schema (allowlist)
class EmployeeResponse(BaseModel):
    model_config = ConfigDict(
        from_attributes=True
    )
    id:    int
    name:  str
    email: EmailStr
    age:   int | None
    ...
    # deleted_at is NOT here
    # → never sent to the client!

The rule: If it is not declared in the response schema, it does not exist in the API response. New database columns are hidden by default. You must opt-in to expose a field.

Different Shapes: List vs Detail

You can define different response schemas for different endpoints:

GET /employees (list)
class EmployeeListResponse(BaseModel):
    model_config = ConfigDict(
        from_attributes=True
    )
    id:    int
    name:  str
    email: EmailStr
    age:   int | None
    # NO departments or addresses
    # → lightweight for lists
GET /employees/{id} (detail)
class EmployeeResponse(BaseModel):
    model_config = ConfigDict(
        from_attributes=True
    )
    id:               int
    name:             str
    email:            EmailStr
    age:              int | None
    departments:      list[DepartmentMinimalResponse] | None
    addresses: list[AddressResponse] | None
    # Full detail with addresses

Why separate schemas?

  • Performance: List endpoints skip heavy nested data (addresses, full relations)
  • Clarity: The Swagger docs show exactly what each endpoint returns
  • Flexibility: Change the detail shape without affecting the list

Filtering Soft-Deleted Nested Data

An employee may have soft-deleted addresses in the database. The response schema should only show active ones:

# On the ORM model:
class Employee(Entity):
    addresses: Mapped[list["Address"]] = relationship(...)

    @property
    def addresses(self) -> list["Address"]:
        return [a for a in self.addresses if a.deleted_at is None]

# The response schema reads from that property:
class EmployeeResponse(BaseModel):
    model_config = ConfigDict(from_attributes=True)
    ...
    addresses: list[AddressResponse] | None
    # Pydantic reads employee.addresses (the property)
    # → soft-deleted addresses are never serialized

Pattern: from_attributes=True reads Python @property methods too, not just columns. Use properties to compute filtered or derived data that response schemas can pick up.

Before & After: Full Comparison

Before (raw dicts)
  • Router accepts body: dict = Body(...)
  • Service manually checks isinstance(name, str)
  • Email is just str with min_length=1
  • No age validation at all
  • Every endpoint calls .to_api_dict()
  • deleted_at exposed in every response
  • No separate list vs detail shapes
  • Swagger docs show generic dict
After (Pydantic schemas)
  • Typed EmployeeCreate / EmployeeUpdate
  • Pydantic validates before service runs
  • EmailStr validates email format
  • AddressCreate: @model_validator for country-specific postal length

  • Swagger shows exact request/response shapes
